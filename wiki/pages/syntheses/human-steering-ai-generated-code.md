## 결론

사람은 AI가 코드를 만들기 전에 의도와 구조를 결정하고, 구현 중에는 작은 단위로 방향을 교정해야 한다. 구현 뒤에는 다음 변경을 이끌 수 있을 만큼 시스템을 이해해야 한다.

두 영상은 서로 다른 시점을 다루지만 같은 문제를 푼다. Dex Horthy는 잘못된 코드가 대량으로 만들어지기 전에 사람의 판단을 앞에 배치한다. Geoffrey Litt는 구현 속도보다 사람의 이해가 느릴 때 생기는 인지 부채를 줄인다.

> 변경 전에 정렬한다 → 작은 단위로 구현하고 검토한다 → 이해를 확인한다 → 다음 변경에 그 이해를 사용한다

## 변경 전: 의도와 코드 형태를 정한다

모든 작업에 긴 설계 과정이 필요하지는 않다. 그러나 오해를 되돌리는 비용이 큰 변경은 코드를 만들기 전에 다음 내용을 정한다.

1. 사용자 요구사항: 어떤 문제를 해결하며 성공을 무엇으로 확인할지 정한다.
2. 시스템 구조: 서비스, API, 정보, 큐와 저장소의 경계를 정한다.
3. 프로그램 설계: 타입, 함수 형태, 파일 배치, 호출 흐름과 의존 방향을 정한다.
4. 구현 순서: 사용하거나 시험할 수 있는 작은 수직 단위로 작업을 나눈다.

이 단계의 목적은 AI에 더 긴 지시를 주는 데 있지 않다. 사람이 비용이 큰 결정을 먼저 검토해, 잘못된 방향으로 빠르게 구현되는 일을 줄이는 데 있다.

## 변경 중: 작은 단위로 검토하고 다시 지시한다

AI가 전체 계층을 한꺼번에 만들게 두면 문제를 발견할 때 변경량이 이미 커질 수 있다. 대신 사용자에게 보이는 경로 하나를 저장소와 서비스까지 연결하는 수직 단위로 구현한다.

각 단위가 끝나면 동작, 코드 형태, 기존 구조와의 관계를 확인한다. 방향이 다르면 다음 단위로 넘어가기 전에 고친다. 테스트와 자동 리뷰는 이 판단을 돕지만, 장기 유지보수성을 대신 판정하지는 못한다.

## 변경 후와 병행: 이해를 작업 산출물로 만든다

코드가 맞게 동작해도 사람이 구조와 동작을 설명하지 못하면 다음 변경을 이끌기 어렵다. 이때 알맞은 이해 자료는 지식 격차에 따라 달라진다.

| 이해 대상 | 알맞은 산출물 | 확인 방법 |
| --- | --- | --- |
| 구조와 책임 | 설명 문서, 파일·호출 흐름 | 주요 구성 요소와 변경 이유를 설명한다 |
| 규칙과 예외 | 질문, 예측 문제 | 입력이나 조건이 바뀔 때의 반응을 예측한다 |
| 동적 동작 | 작은 인터랙티브 모델인 microworld | 상태와 입력을 바꾸며 시스템 반응을 확인한다 |

설명을 읽은 사실만으로 이해를 확인할 수는 없다. 질문에 답하거나 반응을 예측하고, 작은 모델을 직접 조작해야 멘탈 모델의 빈틈이 드러난다.

## 작업 크기에 따른 적용

| 작업 | 권장 개입 |
| --- | --- |
| 문구 수정, 명확한 재현이 있는 작은 버그 | AI가 바로 구현하고 가볍게 검토한다 |
| 여러 모듈을 건드리는 중간 변경 | 요구사항과 구조를 한 문서에서 정리하고 작은 단위로 구현한다 |
| 핵심 흐름, 대규모 기능, 되돌리기 어려운 변경 | 사용자 요구사항부터 프로그램 설계까지 검토하고, 수직 단위마다 코드와 동작을 확인한다 |
| AI가 만든 코드를 팀이 계속 운영해야 하는 변경 | 설명, 질문 또는 microworld를 남기고 팀의 이해를 확인한다 |

## 위험 신호

- AI가 만드는 변경량이 사람이 읽고 설명할 수 있는 속도를 계속 앞선다.
- 테스트는 통과하지만 작은 변경이 여러 파일과 모듈을 반복해서 건드린다.
- 검토에서 사용자 의도나 구조 결정을 처음 논의한다.
- 장애가 생겼을 때 팀이 코드를 다시 이해하는 데 복구 시간 대부분을 쓴다.
- 다음 작업을 지시하려면 먼저 이전 변경의 의도와 구조를 역추적해야 한다.

## 적용 원칙

- hypothesis: 사전 설계와 사후 이해는 대체 관계가 아니다. 같은 변경에서 둘 다 필요할 수 있다.
- hypothesis: 변경 위험이 클수록 사람의 판단을 더 앞에 배치하고 구현 단위를 더 작게 나눠야 한다.
- hypothesis: 설명 자료는 문서 완성도가 아니라 다음 변경을 정확히 예측하고 지시할 수 있는지로 판단해야 한다.
- hypothesis: 테스트 통과, 코드 리뷰, 사람의 이해는 서로 다른 실패를 막으므로 하나를 다른 하나의 대체물로 취급하면 안 된다.
